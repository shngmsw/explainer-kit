# zukai-onepager — 前提知識なしで読める1枚HTML図解

## 目的

対象（コードベース、システム、業務フロー、企画、なんでも）を理解し、
**その分野に詳しくない社会人が1回読んで仕組みがわかる、自己完結のスクロール1枚HTML** を作る。

出力はローカルHTMLファイル1つ。Artifact公開・共有は指示がない限りしない。

## 読者像

**その領域の専門家ではないが、仕事はできる大人。** 他部署の担当者、クライアントの
窓口、着任したばかりの管理職あたりを想定する。

- 前提知識は無いが、読解力と業務経験はある。**噛み砕くのは内容であって、言葉づかいではない。**
- 業務文書として成立する日本語で書く。フリガナ、幼児語、絵本調の語りは使わない。
- 逆に、知っている前提で押し切るのも失敗。専門語を無説明で連発しない。

## 3原則

### 1. 難しさは説明で解く。言葉を子供向けにしない

- 専門語・カタカナ語は**使った場所で即開き**、さらに巻末の**用語集**に収録する。
  開かずに連発するのが最頻出の失敗（例:「決済事業者」を14回無説明で使う）。
- 横文字は可能なら平易な日本語に置き換える（「リードタイム」→「申請から反映までの日数」）。
  置き換えられない定着語はそのまま使い、初出で1行説明を添える。
- 登場する要素は**役割がわかる呼び名**を与え、ページ全体で統一する。正式名は併記する
  （例: `batch` →「収集処理（batch）」、`plugin` →「表示側（plugin）」）。
  対象が社内向け・非エンジニア向けで、砕けた擬人化（「あつめる係」等）が有効だと
  判断した場合はそれを選んでもよいが、既定は役割名とする。
- 1セクション1メッセージ。言いたいことが2つあればセクションを分ける。

### 2. 図解は各セクションに置く

- **主要セクションすべてに最低1つのインラインSVG図解**。図解を冒頭の1枚に
  集約して残りを文字壁にしない（これも頻出の失敗）。
- 図は装飾ではなく、そのセクションの主張そのものを描く。流れは矢印で見せる。
- **登場要素ごとに色を1色決め、ページ全体で貫く**。本文の強調・図・カード・用語集で
  同じ要素は常に同じ色。セクションごとに配色を変えない。

### 3. 器は1枚、語りは毎回設計する

固定するのは器だけ: **自己完結のスクロール1枚HTML**（外部依存はWebフォントまで。
JSは原則不要）。

**章立て・語り口はテンプレにせず、毎回トピックから設計する。** 「どの順で見せたら
この読者が一番腑に落ちるか」を先に考える。時系列で追う、1日の流れとして描く、
1件のデータを追跡する、失敗例から始める——トピックに合う語りを選ぶ。

使いどころがあれば効く道具（毎回入れる義務はない）:

- 読者が最初に抱く疑問で始める導入（「記事の中の数字は、誰がいつ更新しているのか」）
- 登場要素を全部出す全体像の図
- 「勝手には動かない」系の安全装置・例外の章
- 用語集、要素ごとのまとめ

## ビジュアルの世界観

**毎回トピックに合わせて1つ選び、全体で貫く**（紙のノート風、黒板風、路線図風、
設計図風など）。既定テーマは持たない。管理画面風・Bootstrap風の無個性なUIにしない。
一方で、装飾過多で内容より雰囲気が勝つのも避ける。読み手は仕事でこれを読む。

## 図解の描き方 — svg-diagram に従う

### 必須の宣言

各セクションのインラインSVGは、外部スキル `svg-diagram`
（https://github.com/bybit-exchange/svg-diagram）のハウススタイルで描く。
**自己流の座標決めをしない。**

適用するのは svg-diagram の「レイアウト算術」全部である。

- 箱の高さ: font-size × 3。1行増えるごとに font-size × 1.5 を足す
- ベースライン: 箱の中心 y + font-size × 0.35（`<text y>` は上端ではなく baseline）
- コネクタ: 同軸なら `L`、曲がるなら `C` / `Q`。直角エルボー禁止
- 切り欠き矢印マーカー: `markerUnits="userSpaceOnUse"` を明示。始点は元の箱 +5px、
  終点は先の箱 −11px（5px のクリアランス + 6px の矢尻）
- ブロック間隔: 25–30px
- viewBox 余白: 20–25px（上端はタイトルから測る）
- 文字幅の見積もり表で右端が隣に食い込まないか確認する（CJK は font-size と同幅）
- XML エスケープ（`&` → `&amp;`、`<` → `&lt;`）
- 描画順: 背景（点線グループ枠）→ 線 → 箱と文字 → 跨ぎ線
- svg-diagram の検証チェックリストを図ごとに通す

### 読み込み方

作図の前に `~/.claude/skills/svg-diagram/SKILL.md` を読む。

無ければユーザーに次を案内する（**勝手にインストールしない**）:

```
npx skills add bybit-exchange/svg-diagram -g
```

その回だけの代替として、`https://raw.githubusercontent.com/bybit-exchange/svg-diagram/main/SKILL.md`
を作業用ディレクトリに取得して読んでもよい。ルールは適用できるが、この方法では
svg-lint が手元に無いので後述の lint ゲートは使えない。その旨をユーザーに伝える。

### 本スキルが上書きする点

svg-diagram と食い違う箇所は本スキルが優先する。

| 項目 | svg-diagram | 本スキル |
|---|---|---|
| 出力先 | `assets/*.svg` に書いて Markdown から参照 | **HTML にインライン埋め込み**（`<figure>` 内の `<svg>`）。ファイルには出さない |
| フォント | 中国語圏3書体の並び | 日本語フォントを先頭に置き、必須の3書体は後ろに残す |
| 図のタイトル | 図の中にタイトルを置く前提 | 見出しと `<figcaption>` があるので必須ではない |
| 編集ワークフロー | 変更点を集めてから一括適用 | 使わない。一発で仕上げてチェックリストと lint で検品する |

**フォント**: 読者は日本語話者なので、日本語フォントを先頭に置く。svg-diagram が
必須とする3書体（`'PingFang SC'` → `'Microsoft YaHei'` → `'Noto Sans CJK SC'`）は
その順序を保ったまま後ろに残す。SVG ごとに `<style>` で宣言する。ページ CSS に
頼らない（`html-to-deliverable` で画像化したときに効かなくなるため）。

```xml
<style>
  text { font-family: 'Hiragino Sans', 'Yu Gothic', 'Meiryo', 'Noto Sans CJK JP', 'Noto Sans JP', 'PingFang SC', 'Microsoft YaHei', 'Noto Sans CJK SC', system-ui, sans-serif; }
</style>
```

ページで Web フォント（例: Noto Sans JP）を読み込んでいる場合は、それをさらに
先頭に置く。

**色**: 3原則の「登場要素ごとに1色」は、svg-diagram の**5つの意味色トリプル
（fill / stroke / text）**から要素ごとに1トリプルを割り当てて実現する。

| 意味 | fill | stroke | text | 矢印 |
|---|---|---|---|---|
| 入力・起点 | `#dbeafe` | `#3b82f6` | `#1e40af` | `arrow-blue` `#3b82f6` |
| 処理・進行中 | `#fef3c7` | `#f59e0b` | `#b45309` | `arrow-orange` `#f59e0b` |
| データ・出力 | `#d1fae5` | `#22c55e` | `#166534` | `arrow-green` `#22c55e` |
| 分析・特殊 | `#f3e8ff` | `#a855f7` | `#6b21a8` | `arrow-purple` `#a855f7` |
| 注意・例外 | `#fce7f3` | `#ec4899` | `#9d174d` | `arrow-red` `#ef4444` |

主要要素は5つまでに絞る。6つ目以降は基本色（主要テキスト `#1e293b`、
副次テキスト `#64748b`、抑えたテキストと既定の矢印 `#94a3b8`）と点線グループ枠
（fill `#f8fafc` / stroke `#94a3b8`）で描く。

本文の強調・カード・用語集の色には、図と**同じ hex をそのまま CSS に使う**。
図と文で色がずれるのを防ぐため。

**ビジュアルの世界観との関係**: 世界観（紙のノート風、路線図風など）は**ページ側**
——背景・見出し・罫線・カード・タイポグラフィ——で表現する。**図の中はハウス
パレットのまま**にする。理由は3つある。lint を通る、どの背景でも読める、納品変換で
画像化しても崩れない。SVG の最初の要素として viewBox 全体を覆う
`<rect fill="#ffffff"/>` を置き、図はページ上で「白いカード」として載せる。

**マーカー id**: 1ページに複数の SVG が並び、id 名前空間は共有される。`<defs>` の
マーカー id は**図ごとに一意**にする（例: 3つ目の図なら `arrow-f3`、`arrow-blue-f3`）。
同じ `id="arrow"` を複数の SVG で使うと、ブラウザは最初の定義しか参照せず矢印の色が
混ざる。

**図のタイトル**: セクション見出しと `<figcaption>` があるので、SVG 内タイトルは
必須ではない。置く場合は svg-diagram の余白計算（タイトル上端から 20–25px）に従う。

### 作図の進め方

svg-diagram 自身が「一発生成はサブエージェントで」と勧めている。図の枚数が多いので
これに従う。

1. **本体側で各図の仕様を決める**: その図の1メッセージ、登場要素と割り当てる
   トリプル、流れ（何から何へ）、想定幅（svg-diagram の Display size 表: 単純な列挙
   400px、フロー 600–700px、構成図 700–800px）、マーカー id の接尾辞
2. **図ごとにサブエージェントへ委任する**。サブエージェントには次を伝え、
   `<svg>…</svg>` 断片だけを返させる
   - svg-diagram の SKILL.md を読んでから描くこと
   - 上の上書き点（インライン、日本語フォント、パレット、一意な id、白い背景 rect）を
     守ること
   - 完成前に svg-diagram の検証チェックリストを自分で通すこと
3. **本体側が HTML に組み込む**
4. **lint ゲートを通す**（次項）

### lint ゲート

HTML が組み上がったら、同梱スクリプトで全インラインSVGを検査する。

```
python3 <このスキルのディレクトリ>/scripts/lint-inline-svg.py <出力HTML>
```

`<このスキルのディレクトリ>` は、このSKILL.mdが置かれているディレクトリを指す。
プラグイン経由なら `~/.claude/plugins/*/explainer-kit/skills/zukai-onepager/`、
symlink インストールなら `~/.claude/skills/zukai-onepager/` になる。
場所がわからなければ `find ~/.claude -name lint-inline-svg.py` で探す。

**エラーもワーニングも 0 が合格。** 指摘には修正値（actual → expected）が付くので、
それに従って直して再実行する。ワーニングを「推奨だから」と残さない。

svg-diagram が見つからないときはスクリプトが案内を出して終了コード 2 で止まる。
その場合はユーザーにインストールを案内し、svg-diagram のチェックリストを手で通す。

## 手順

1. 対象を理解する（コード・ドキュメント・会話を読む。わからないまま書かない）
2. 登場要素を洗い出し、呼び名と色（意味色トリプル）を決める
3. このトピックに合う語り（見せる順番）を設計し、各章の「1メッセージ」と図解の内容を決める
4. 図の仕様を決め、サブエージェントに描かせる（「図解の描き方」）
5. HTMLを書く
6. lint ゲートを通す（`scripts/lint-inline-svg.py`。エラー・ワーニングとも 0 まで直す）
7. 検品する（下のチェックリスト）

## 納品用に清書する

説明が済んで「後で読む用」「納品用」のドキュメントが要る場合は、HTML を正本に
したまま `html-to-deliverable` で Word / PDF / Google ドキュメントに変換する。
インラインSVGは自動で画像化されるので**作図をやり直さない**。

## 検品チェックリスト

- [ ] 主要セクションすべてにSVG図解があるか（1枚集約になっていないか）
- [ ] `scripts/lint-inline-svg.py` がエラー 0・ワーニング 0 で通っているか
- [ ] 各SVGが日本語優先のフォントスタックを `<style>` で自前に持っているか
- [ ] マーカー id が図ごとに一意か（`arrow-f1`、`arrow-f2` のように）
- [ ] 各SVGの先頭に viewBox 全体を覆う `<rect fill="#ffffff"/>` があるか
- [ ] 本文中の専門語・カタカナ語がすべて即開きされ、用語集にも載っているか
- [ ] 要素の呼び名と色が本文・図・カードで一致しているか（同じ hex を使っているか）
- [ ] 語りの構成がテンプレの流用でなく、このトピックのために選ばれているか
- [ ] 幼児語・フリガナ・過剰な比喩・絵文字の多用など、業務文書として不自然な表現が
      残っていないか（社外に出しても支障ない文体か）
- [ ] 逆に、無説明の専門語で読者を置き去りにしている箇所がないか
